The finding: one folder tree is answering two different questions

The migration task assumed the open question was where the boundary between lib/ root and lib/kits/ falls. Measuring every file's observable properties says the problem is one level up. Two independent questions are being asked of one directory structure, and it can only answer one:

What does it attach to?

GH.prototype, a window namespace, or Alpine.data. Structural, mechanical, one grep each. The folders do encode this, and once measured properly they encode it almost perfectly.

answerable by folder
When does it load?

The boot chain loads files unconditionally, so every loader page pays for them. That set spans all three folders and is written down nowhere. It is a real cost and a real category, and it is orthogonal to attachment.

not answerable by folder

This is why every attempt at a single rule has failed. "Portable capability" failed because it was unmeasurable. A boundary drawn on boot would break the one clean category there is. The way out is to let attachment decide the folder and give boot a name of its own.

The options

Four, including dissolving kits entirely. The measurement rules one out and leaves the rest as genuine choices.

The proposed concept

Three categories on the browser side, each admitted by one grep, plus one declared list that is not a folder. A file's folder answers what it attaches to. The manifest answers when it loads. Neither question is asked to carry the other.

The fourth thing: a boot manifest, not a folder.
The boot-loaded files stay wherever their attachment puts them, and the boot chain's contents become an explicit declared list rather than a set of gh.load calls buried in gh-boot.js. That makes the one number nobody can currently see (what every page pays for) visible and testable, and it is what lets the folders stop trying to encode it.

Found on the way, unrelated to the split

lib/repo-config-cache.js and lib/alpineComponents/estate.js each carry a literal NUL byte, used deliberately as a string delimiter. Both behave correctly and the pre-build escapes them, so nothing is broken at runtime. But grep classifies both files as binary and skips them silently, which means they are invisible to npm run code-survey, the link survey, and every grep -r in the repo. That matters here specifically, because the migration rule is a grep: two of the files being sorted cannot be seen by the thing sorting them. One character each fixes it (\0 as an escape rather than the raw byte), with no change to behaviour.
