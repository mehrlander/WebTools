Code layers

files under lib/ · change · measured at by npm run code-shape

This guide concerns the placement of source files within lib/, and the rule by which placement is decided.

The repository loads most of its browser code at runtime through gh.load. Three directories hold that code. lib/alpineComponents/ holds files, each registering an Alpine component. lib/kits/ was established for themed logic libraries, each registering a single namespace on window, and holds . lib/ root holds the loader and the chain that boots it, and, accumulated alongside them, further files that register a window namespace and are in that respect indistinguishable from the contents of lib/kits/.

On 2026-07-26 a task was opened to move the misfiled files. It identified eight, on the rule then understood: a kit registers a namespace, and scaffolding extends GH.prototype.

On 2026-08-06 PR #362 landed docs/code-layers.md, supplying a further rule: a kit is a capability that would hold in any repository, while a module of the same shape carrying this repository's own domain belongs in lib/ root. The rule was applied to the task's file list that day.

It was measured that day also. Counting runtime dependencies on the loader, seven of the twenty-one files in lib/kits/ were found unable to travel to another repository, and six files in lib/ root were found to carry no such dependency. The rule was retracted. PR #366, open at this writing, carries the retraction. The task's progress log records that placement is thereafter undecided, and that nothing moves until it is decided.

No measurement had been offered of what the two folders do sort on. This guide supplies one, and three findings of it correct the record.

First, traffic.js does not extend GH.prototype. It wraps window.fetch. (lib/traffic.js, now under kits/) The claim that it does appears in a comment within the file, and the task adopted it.

Second, kits/build.js (now at lib/ root) does extend GH.prototype, which lib/kits/README.md states a kit cannot do.

Third, the earlier counts were taken over the files' comments as well as their code, and a file's header commonly describes a dependency the file does not have. Measured over code alone, of the files in lib/kits/ carry a loader dependency, not seven, and files in lib/ root carry none, not six. The correction runs in the retraction's favour: the disparity it found is wider than it recorded.

Two matters are not in dispute. Every file in lib/alpineComponents/ registers Alpine.data, and that boundary holds without exception. Both remaining folders hold files of one shape: a window namespace, Alpine-free, pure logic.

Fourth, and found on 2026-08-07 while the split was being derived: the boundary is written three ways, not two. Beside GH.prototype.x = and an alias off the class, there is an alias off an instance, window.gh.constructor.prototype, which is how lib/gh-boot.js wraps .load. A detector reading only the first two forms classifies the repository's own boot file as a kit. This guide had held that file in lib/ root by a reason written by hand. The survey was corrected, and the file is now placed by the same rule as every other.

A third candidate rule was proposed on 2026-08-07: that a kit is logic used across more than one page. It was measured the same day, by counting the distinct non-test files that reference each module's namespace. The two folders returned medians of 5.5 and 4.0 over ranges of one to twenty-nine and two to thirty-one; the most-referenced logic module in the repository sits in lib/ root, and the two least-referenced are kits. The rule was not adopted. A second objection was recorded: reach changes when an unrelated page is added or removed, so a file would change folders without itself changing, and no test could hold the boundary without churn.

On 2026-08-07 the question was decided. The two folders are one category. Every file registering a window namespace is a kit; lib/ root retains the loader, the files extending its prototype, and the boot bundles. Boot membership, which is a cost rather than a structure, passes to a declared manifest. Twenty files move, one moves the other way, and one is deleted. The alternatives are preserved under Options, and the sequence under Migration.

The rule states where a file belongs. When this guide was written the migration had not run and the tree and the rule disagreed by twenty-two files. The migration ran on 2026-08-08: twenty-two kits moved (the settled twenty plus content-registry.js and estate-search.js, added while the decision was being made and kits by the rule before it landed), build.js moved to lib/ root, the dead diagnostic file was deleted, and tools/test/code-layers.test.mjs now holds the boundary. The snapshot rows behind the Shelf and Migration tabs are the 2026-08-07 derivation, kept as the record the decision was made from; npm run code-shape reads the current tree.

What a file attaches to the folders encode this

GH.prototype, a window namespace, or Alpine.data. One grep each, and once the detector is right the folders sort on it almost perfectly.

When a file loads nothing encodes this

The boot chain loads files unconditionally, so every loader page pays for them. That set spans all three folders and is written down nowhere. Orthogonal to attachment, which is why one tree cannot carry both.

Two corrections from measuring rather than grepping. traffic.js does not extend GH.prototype; it wraps window.fetch, and only a comment says otherwise, so the task lists it as scaffolding on the strength of prose about the code. kits/build.js does extend it, from the shelf whose README says a kit cannot. Counting comments as code also made every kit look Alpine-coupled when none is.

The fourth thing: a boot manifest

The boot-loaded files stay wherever attachment puts them, and the boot chain's contents become an explicit declared list rather than gh.load calls buried in gh-boot.js. That makes the one number nobody can currently see, what every page pays for, visible and testable. It is what lets the folders stop trying to encode it.

Why it holds this time

Each rule above is a grep, so a test can assert it and the boundary stops depending on anyone remembering. The retracted rule failed precisely because it sorted on something no test could check.

Found on the way, unrelated to the split

lib/repo-config-cache.js and lib/alpineComponents/estate.js each carry a literal NUL byte, used deliberately as a string delimiter. Both behave correctly and the pre-build escapes them, so nothing is broken at runtime. But grep classifies both as binary and skips them silently, so they are invisible to npm run code-survey, the link survey, and every grep -r. That matters here specifically, because the migration rule is a grep: two of the files being sorted cannot be seen by the thing sorting them. One character each fixes it (\0 as an escape rather than the raw byte), with no change to behaviour.
